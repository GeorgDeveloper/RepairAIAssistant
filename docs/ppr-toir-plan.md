## 1. Что уже есть в программе

| Модуль | Роль сейчас |
| --- | --- |
| `assistant-core` | API, расчёты, доступ к MySQL |
| `assistant-web` | Страницы Thymeleaf, меню |
| `assistant-base_update` | Перенос нарядов из CMMS (SQL Server) в MySQL |
| `assistant-ai`, `assistant-yandexbot` | Ассистент и бот, к графику ППР не относятся |

Уже закрывает часть ТЗ, но как **просмотр факта из CMMS**, а не как планирование:

| Требование ТЗ | Где это уже есть | Чего не хватает |
| --- | --- | --- |
| Учёт выполненных ППР, план/факт | Меню «ППР»: `/dinamic_pm`, `/pm`, `/pm_tag_bd`. Данные пишет `PreventiveMaintenanceTransferService` в `pm_maintenance_records` | Свой план-график, шаблоны, интервалы, утверждение |
| Поломки, простои, топ причин | Меню «Поломки», `equipment_maintenance_records` | Сменный журнал как часть наряда ППР, запуск RCA |
| Диаграмма Ганта | `/gantt` — Гант **поломок**, не плана ППР | Гант плановых нарядов по линиям и интервалу |
| График на год с равномерным распределением | «Диагностика → График диагностики», `DiagnosticsScheduleService` | Это диагностики B/K/y/T, не ППР / проверка АБУ / замена масла |
| База знаний по сложным ремонтам | `/long_report`, отчёты диагностики | Привязка результата расследования к плану ППР |
| Справочники и чертежи | `/manuals` | Паспорт объекта ремонта и нормативы периодичности |
| Список линий | `main_lines_online`, ключевые линии на дашборде | Реестр основного оборудования с карточками и нарядами |

## 2. Что ТЗ просит сверх текущего контура

Разделы 3.1–3.8 описывают полноценную систему ТОиР: паспорта до детали, материалы, акты, RCA («5 почему», Исикава), SAP, 500 пользователей, LDAP. Это не одна поставка.

В конце ТЗ («Особые требования») записан конкретный контур, ради которого делается модернизация. Он и есть первая очередь:

1. Шаблоны нарядов: вид работ, длительность, описание.
2. Список основного оборудования.
3. К каждой единице можно подключить сколько угодно шаблонов.
4. Цепочка утверждения изменений по нарядам.
5. План считается из подключённых нарядов и интервала. Следующее выполнение = дата закрытия текущего наряда + интервал из шаблона.
6. При закрытии можно указать дополнительные работы, которые сделали сверх наряда.
7. Три плановых типа: **проверка АБУ**, **ППР**, **замена масла**.
8. Четвёртый тип: **ремонт по состоянию** — разовая работа на одну линию, она попадает в график один раз.
9. Четыре вида одного и того же плана:
   - интерактивная карта линий (активные и просроченные наряды);
   - список с фильтром по участку, типу работ, оборудованию;
   - Гант с выбором интервала и линий;
   - план на согласование производству: неделя, месяц, квартал, год.
10. Отчёты: график выполнения по участкам; % по трём категориям; общий % за месяц; топ причин переноса; при закрытии после срока и допуска — обязательные причина и обоснование.

Сценарий 8.2 ТЗ (внеплановый ремонт и автоматический RCA) помечен в ТЗ как «на перспективу». В первую очередь его не берём.

## 3. Границы очередей

### Очередь 1 — можно формировать и вести график

Реестр основного оборудования, шаблоны нарядов, привязка к оборудованию, расчёт дат, список работ, закрытие с доп. работами и причиной просрочки, ручной перенос срока.

### Очередь 2 — согласование и остальные виды плана

Цепочка утверждения, Гант, недельный/месячный/квартальный/годовой план для производства.

### Очередь 3 — карта и стандартная отчётность

Подсветка линий, проценты выполнения, топ причин переноса, выгрузка Excel.

### Очередь 4 — стыковка с тем, что уже работает

Факт из CMMS, поломки, отчёты о сложных ремонтах, диагностика. Без замены текущих отчётов.

### Очередь 5 — остальной текст ТЗ, отдельным решением

Полный паспорт до узла и детали, материалы и запчасти, дефектные ведомости и акты, RCA, SAP/SPOCS, LDAP, английский интерфейс, требование «500 пользователей / отклик 2 секунды». Эти пункты в чеклисте есть, но к ним не переходить, пока очереди 1–3 не приняты.

## 4. Модель данных первой очереди

Скрипты класть в `script/`, по образцу `script/create_diagnostics_schedule_tables.sql`.
Код: сущности и API в `assistant-core`, страницы в `assistant-web`, пункт меню рядом с «ППР».

| Таблица | Назначение |
| --- | --- |
| `ppr_equipment` | Основное оборудование: код, название, участок, линия, статус (в работе / в ремонте / на консервации / списан), место установки |
| `ppr_work_template` | Шаблон наряда. Тип: `ABU_CHECK`, `PPR`, `OIL_CHANGE`, `CONDITION`. Описание, норма длительности, интервал и его единица (день / неделя / месяц / час наработки). Для `CONDITION` интервал пустой, работа разовая |
| `ppr_equipment_template` | Какие шаблоны подключены к оборудованию. Дата начала действия. Для разовой работы — плановая дата |
| `ppr_work_order` | Конкретный наряд на дату: оборудование, шаблон, план, факт начала/окончания, статус, исполнитель, % готовности, доп. работы при закрытии |
| `ppr_work_order_event` | Журнал: создание, перенос, утверждение, закрытие. Кто, когда, причина, обоснование |
| `ppr_approval` | Шаг цепочки: черновик → на согласовании → утверждён / отклонён. Пока достаточно двух ролей: планировщик и главный механик |

Правило расчёта следующей даты (п. «особые требования»):

- плановый тип: `следующая_дата = дата_закрытия_текущего_наряда + интервал_шаблона`;
- если наряд ещё ни разу не закрывали: первая дата = дата начала привязки шаблона к оборудованию;
- ремонт по состоянию: одна запись на выбранную дату, после закрытия новая сама не создаётся;
- перенос срока не меняет интервал шаблона, меняет дату конкретного наряда и пишет причину в `ppr_work_order_event`;
- закрытие позже плановой даты плюс допуск (допуск — настройка, по умолчанию 0 дней) требует причину и обоснование.

Статусы наряда: `DRAFT`, `PENDING`, `APPROVED`, `IN_PROGRESS`, `DONE`, `RESCHEDULED`, `CANCELLED`.

Версионность годового плана из п. 3.3.2.14 на очереди 1 не делаем: журнал событий наряда уже хранит переносы. Снимок утверждённого плана — очередь 2, таблица `ppr_plan_version`.

### Этап 2. Шаблоны нарядов

Статус этапа: **не начато**

- [ ] SQL: `ppr_work_template`
- [ ] Справочник из четырёх типов. Три плановых нельзя сохранить без интервала. `CONDITION` нельзя сохранить с интервалом

- [ ] Завести стартовые шаблоны: проверка АБУ, ППР, замена масла — после того как заказчик даст интервалы и длительность. До этого в системе только пустые типы
- [ ] Проверка в браузере: нельзя сохранить плановый шаблон без интервала; разовый шаблон сохраняется без интервала

### Этап 3. Привязка шаблонов к оборудованию

Статус этапа: **не начато**

- [ ] SQL: `ppr_equipment_template`
- [ ] В карточке оборудования: список подключённых шаблонов, добавление любого числа, дата начала, для разовой работы — дата выполнения и линия
- [ ] Одна и та же пара «оборудование + шаблон» не дублируется, пока предыдущая привязка активна
- [ ] Отключение привязки прекращает генерацию следующих нарядов и не удаляет историю
- [ ] Проверка: к одной линии подключены проверка АБУ, ППР и замена масла; отдельно создана разовая работа на одну дату

### Этап 4. Расчёт графика и список работ

Статус этапа: **не начато**

- [ ] SQL: `ppr_work_order`, `ppr_work_order_event`
- [ ] Сервис генерации в `assistant-core`. Запуск вручную кнопкой «Сформировать график» на выбранный горизонт (месяц / квартал / год) и повторный запуск без дублей: если наряд на эту привязку и дату уже есть, второй не создаётся

- [ ] Алгоритм: для каждой активной привязки взять дату последнего закрытого наряда, прибавить интервал, поставить наряд внутрь горизонта. Если закрытий не было — старт от даты привязки. Разовая работа попадает один раз, если её дата внутри горизонта

- [ ] Проверка: после закрытия наряда повторная генерация ставит следующий наряд на `дата закрытия + интервал`, а не на старую календарную сетку
